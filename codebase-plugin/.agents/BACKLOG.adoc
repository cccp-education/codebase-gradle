== ✅ EPIC CB-STORE-UNIFY — Consolidation `codebase.rag.VectorStore` JDBC legacy — ✅ CADUQUE (S-206)

_Source_ : décision archi S-097 (consolidation JDBC legacy HORS SCOPE de
CDX-RAG-SOCLE, reportée à un EPIC futur dédié).
_Doc cadrage_ : `CADRAGE_EPIC_CB_STORE_UNIFY.adoc` (côté codex-gradle).

=== Constats (audit S-206 pré-coding)

. Cadrage CB-STORE-UNIFY existant trop simpliste : prévoyait "remplacer les
  appels par `searchBlocking` (API identique)" — faux. Les APIs sont très
  différentes.
. `RagVectorStore` (R2DBC socle, `codebase.store`) : `searchBlocking(query,
  topK)` seulement — recherche sur corpus documentaire codex (tables
  `codex_documents`/`codex_chunks`, métadonnées `section_path`,
  `heading_level`, `source_document`).
. `VectorStore` legacy (JDBC, `codebase.rag`) : `initSchema`,
  `ensureSchema`, `insertDocument`, `updateEmbedding`, `fetchAllChunks`,
  `querySimilar`, `countDocuments`, `countChunks`, `findByPackage` —
  ingestion + query du code source du workspace (tables `documents`/
  `chunks`, métadonnées `package_name`, `class_name`, `repo_name`, filtre
  `fileExtension`).
. Consommateurs profonds : `OcrIngestTask`, `MultiChannelContextGraph`
  (utilise les deux stores — legacy pour RAG code, socle pour Docs corpus),
  `KoogAugmentedContextGraph`, `KoogPlanningOrchestrator`,
  `VectorQueryService`, `EmbeddingPipeline`, `PgVectorConfig`, plus 7
  fichiers tests/scénarios Cucumber.
. Usage sémantiquement distinct : le legacy indexe le code source du
  workspace (packages, classes, fileExtension) ; le socle indexe le corpus
  documentaire (livres, PDF, sections AsciiDoc). Les fusionner ferait perdre
