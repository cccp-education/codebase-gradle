=== Phase GREEN — implémentation

`TaskResultVerifier.kt` refondu :

. Surcharge `verify(stdout, stderr, expectedOutput)` ajoutée — 2-arg
  délègue avec `DEFAULT_EXPECTED_OUTPUT`.
. `DEFAULT_EXPECTED_OUTPUT = "BUILD SUCCESSFUL"` const companion +
  `DEFAULT_EXPECTED_OUTPUT_LOWER = "build successful"` (comparaison
  lowercase — bug subtil : `expected` est lowercased mais
  `DEFAULT_EXPECTED_OUTPUT` non lowercased → `isCustomExpected` toujours
  true → tous les tests default cassés. Fix : comparaison avec
  `DEFAULT_EXPECTED_OUTPUT_LOWER`).
. Branche `isCustomExpected` : (1) check `build failed`/`compilation
  error`/`hasActualFailure` → FAILED ; (2) si stdout contains expected
  (case insensitive) → SUCCESS sinon FAILED.
. Branche default : heuristique fallback conservée + `hasActualFailure`
  raffiné.
. `hasActualFailure(combined)` : `FAILED_PATTERN = \\bfailed\\b` findAll
  → any match non précédé de `0 ` ou `no ` (exclut `0 failed`, `no
  failed`).

`StepVerifier.kt` : `resultVerifier.verify(state.lastToolResult, "")` →
`resultVerifier.verify(state.lastToolResult, "", step.expectedOutput)` —
câble le contrat N0 `expectedOutput` du `VibecodingStep` (PLN-VERIFY
S-064).

== Leçons

. **Bug subtil lowercase** : comparer `expected` (lowercased) avec
  `DEFAULT_EXPECTED_OUTPUT` (const non lowercased) → `isCustomExpected`
  toujours true. Fix : const `DEFAULT_EXPECTED_OUTPUT_LOWER` séparée.
  Diagnostic difficile car bytecode décompilé semblait correct — le bug
  était dans la logique de comparaison, pas dans la compilation.
. **Backward compat contrat** : `expectedOutput` custom est maintenant
  comparé au stdout. Les tests StepVerifier qui utilisaient des
  expectedOutput custom " décoratifs " (non comparés avant) doivent être
  adaptés pour utiliser `DEFAULT_EXPECTED_OUTPUT` quand on teste
  BLOCKED/UNKNOWN (qui sont des verdicts heuristiques fallback).
. **Baby-step TDD** : 10 tests RED d'un coup → 1 cycle GREEN → 1 cycle
  REFACTOR (tests StepVerifier adaptés). Pattern efficace pour une
  refonte d'API.
