== Contexte

Session cross-borough déclenchée par un diagnostic IntelliJ : `libs` unresolved
dans `codebase-plugin/build.gradle.kts` à l'ouverture du projet. Investigation
révélant une dérive architecturale majeure : `codebase-gradle/settings.gradle.kts`
faisait `include(":codebase-plugin")` (pattern monorepo), contredisant l'article
0124 « Plugin Indépendant + Racine Consommateur ». Le `codebase-plugin/` était
un build autonome complet (son propre `settings.gradle.kts`, `gradlew`,
`gradle/libs.versions.toml`) mais le catalog `libs` manquait côté plugin —
seul le catalog racine existait.

Parallèlement, lancement de l'EPIC SLD-8 (slider consomme codebase comme socle
LLM unifié). Vérification du socle LLM dans codebase révélant que
`LlmProviderResolver`, `OllamaPool`, `GeminiLlmProvider`, `LlmProvider` sont
tous implémentés et opérationnels — le seul gap est l'absence de `BuildService`
Gradle pont (US-8.1).

== Décisions

. **Architecture restaurée** : `codebase-gradle` redevient une racine
  consommateur (pattern article 0124), `codebase-plugin/` est un build
  indépendant avec son propre catalog. Le nmcp reste côté plugin (c'est lui
  qui publie sur Maven Central).
. **US-8.1 est un chantier codebase-seul** : le socle N1 (`LlmProviderResolver`,
  `OllamaPool`, `GeminiLlmProvider`) était déjà implémenté. Le seul gap était
  le `BuildService` pont Gradle. US-8.2 (câblage slider) est un chantier
  slider-seul.
. **DI native Gradle** (Decision 001 slider) : `LlmBuildService` utilise
  `BuildService<Params>` + `Provider<T>`, pas de conteneur DI externe.
