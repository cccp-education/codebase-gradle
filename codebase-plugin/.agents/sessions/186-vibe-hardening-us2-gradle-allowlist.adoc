== Constat audité (P1 S1)

`ExecGradleTool.validateGradleTask` (`contracts/vibecoding/tools/ExecGradleTool.kt:53-61`)
appliquait 4 regex `GRADLE_BLACKLIST` :
* `clean\s+build` → contournable (`clean  build` double espace passe)
* `--refresh-dependencies` → contournable via variations
* `rm\s` / `delete\s` → couvre pas `sudo`, `curl`, `;`, `|`

Surface d'attaque réelle : un agent LLM peut produire des variantes
lexicales que les regex ne couvrent pas, et exécuter dans le workspace
sans surveillance.

== Leçons

* Pattern US-1 (allowlist par token + deny-list second ride) se transpose
  directement à un tool Gradle — la seule différence est la nature des
  tokens (task vs args, vs commande shell monolithique)
* Split par `\\s+` nécessaire car Gradle accepte plusieurs args (flags,
  properties) alors que shell valide la commande entière comme un bloc
* Test `clean  build` (double espace) — cas limite couvert par deny-list
  `clean\\s+build` (regex `\\s+` matche 1+ espaces), confirmé PASS
