== Jardin Secret (Contexte Workspace)

=== Jardin Secret — Filtre d'Intimité

Le **jardin secret** (Cercle 0, workspace racine) est le cercle le plus intime :

* **Pas de versionnage Git** — `workspace/` n'a pas de `.git/`, c'est un design délibéré
* **Historisation par snapshot** — les modifications sont archivées en `configuration/vision-archive/$DATE/`
* **Filtre d'intimité** — les documents y vivent comme "pensées en cours", sans pression de publication

Contrairement aux autres cercles (versionnés, collaboratifs), le jardin secret est **out-of-CVS-system** :
on n'y écrit pas pour être lu — on y écrit pour **clarifier sa propre vision**.

=== Anonymisation — Filtre de Protection des Données

L'anonymisation est le **complément** du jardin secret pour EPIC V-9 :

* **Pipeline OCR→anonymize→pgvector** — tout contenu sensible (documents, images, PDF) passe par l'anonymizer
* **TextAnonymizer** — extraction des données personnelles (Noms, Emails, Tél, Adresse, etc.)
* **Filtre de保护** — les fichiers agentiques de gouvernance ne doivent jamais contenir de données sensibles

=== Impact sur EPIC V-9

L'EPIC V-9 traite des **fichiers agentiques de gouvernance** (AGENT.adoc, INDEX.adoc, SESSION_CHECKLIST.adoc, etc.) situés dans `.agents/` → *cercle 4, mais référence le cercle 0* :

* Les règles agentiques (AGENT.adoc, SESSION_CHECKLIST.adoc) doivent respecter **les 2 filtres** :
  * **Filtre d'intimité** → pas de commit/merge, snapshot horodaté
  * **Filtre d'anonymisation** → zéro donnée personnelle, tout est généré synthétiquement
* L'historisation passe par **snapshot dans `configuration/vision-archive/`**, pas par git

=== Impact sur EPIC V-9

L'EPIC V-9 traite des **fichiers agentiques de gouvernance** (AGENT.adoc, INDEX.adoc, SESSION_CHECKLIST.adoc, etc.) situés dans `.agents/` → *cercle 4, mais référence le cercle 0* :

* Les règles agentiques (AGENT.adoc, SESSION_CHECKLIST.adoc) sont **également valables pour le jardin secret** (copie fichiers, sauvegarde, séparation secrets)
* L'historisation des modifications passe par **snapshot dans `configuration/vision-archive/`**, pas par git
* Les tests et builds doivent respecter les **règles absolues du jardin secret** (aucun secret dans logs, git status seulement)

=== 2. Le Product Vision Board

==== Target Group

* **Direct** : développeurs codebase-gradle, maintainers plugins N1/N2
* **Indirect** : opencode agent, utilisateur final (humain qui dialogue avec opencode)

==== Needs

1. **Vibecoding complet** : le LLM doit manipuler TOUS les fichiers du workspace (non seulement le code applicatif)
2. **Gouvernance exécutable** : les règles agentiques (AGENT.adoc, INDEX.adoc, etc.) doivent être transformées en contraintes exécutables
3. **Pipeline agentique** : les procédures de session (ouverture/fermeture, backup, archive) doivent être automatisées
4. **DAG complet** : tous les fichiers .adoc de governance doivent être analysés, structurés, chunkés, embeddingés, pgvectorisés
5. **Integration opencode** : opencode doit consommer le pipeline Vibecoding pour dialoguer avec le LLM

==== Product

1. **AnalyzeAgent** : analyse les fichiers .adoc de governance, extrait les chunks (rules/concepts/procedures/metadatas)
2. **OntologizeAgent** : mappe chaque chunk sur TAXONOMIE_WORKSPACE (verbe, domaine, DAG level, cercle)
3. **EnforceAgent** : transforme les règles en contraintes exécutables (ToolRegistry pre/post hooks)
4. **ChunkingPipeline** : pipeline complet (scan→chunk→ontologize→store→compile→enforce)
5. **VibecodingGovernanceTask** : tâche Gradle unique pour lancer le pipeline complet

==== Business Goal

* **Critères de succès** :
** 100% des fichiers .adoc de governance anal
ysés/structurés
** 90%+ de chunks extraits correctement (pattern matching + LLM fallback)
** 100% des règles transformées en contraintes exécutables
** 100% des procédures transformées en tâches Gradle
** 0 violations de règles en production (ToolRegistry bloque)

==== Vision

En transformant la littérature agentique textuelle (AGENT.adoc, INDEX.adoc, SESSION_CHECKLIST.adoc, etc.) en chunks ontologisés et contraintes exécutables, le Vibecoding devient un **système agentique complet** qui peut :
- Lire, analyser, et structurer TOUS les fichiers du workspace
- Transformer les règles en contraintes exécutables (ToolRegistry pre/post hooks)
- Automatiser les procédures de session (ouverture/fermeture, backup, archive)
- Fournir un contexte augmenté complet à l'LLM (RAG pgvector + Graphify + EAGER/LAZY)

== Atelier 2 : Personas/Parcours utilisateurs

=== Persona 1 : Développeur codebase-gradle

* **Qui** : Mainteneur du plugin codebase-gradle, expert Kotlin/Gradle/RAG
* **But** : Analyser et structurer les fichiers agentiques/gouvernance, transformer en tâches Gradle
* **Parcours** :
** 1. Git clone codebase-gradle
** 2. ./gradlew vibecodingGovernance --analyze
** 3. Viewer le résultat (chunks ontologisés, rules enforces)
** 4. Intégrer les contraintes dans le build
** 5. Valider avec tests (./gradlew check)

=== Persona 2 : Opencode Agent

* **Qui** : Interface utilisateur terminal qui dialogue avec le LLM via opencode-session-protocol
* **But** : Consommer le pipeline Vibecoding pour obtenir le contexte augmenté complet
* **Parcours** :
** 1. opencode → SessionProtocolTask (SessionPrompt)
** 2. SessionProtocolTask → VibecodingTask (buildContext, callLLM, executeTools)
** 3. VibecodingTask → VibecodingGovernanceTask (analyzer, ontologize, enforce)
** 4. VibecodingGovernanceTask → pgvector (chunks ontologisés)
** 5. pgvector → LLM (contexte augmenté complet)

=== Persona 3 : LLM Agent

* **Qui** : LLM (gemini-1.5-flash, qwen3-coder-next:cloud, etc.) qui reçoit le contexte augmenté
* **But** : Consommer le contexte augmenté (EAGER/LAZY + RAG pgvector + Graphify + Ressources) pour décider
* **Parcours** :
** 1. VibecodingTask → compositeContext (EAGER 40% + RAG 30% + Graphify 20% + Ressources 10%)
** 2. VibecodingGovernanceTask → enrichir EAGER avec chunks ontologisés
** 3. pgvector → répondre aux requêtes par similarité
** 4. Graphify → répondre aux requêtes par relations

== Atelier 4 : Wireframe/Moodboard

=== Wireframes

==== Wireframe 1 : VibecodingGovernanceTask CLI

[source,bash]
----
./gradlew vibecodingGovernance --action <analyze|ontologize|enforce|store|all>

Options:
--analyze    : Scan les fichiers .adoc et extrait les chunks
--ontologize : Mappe les chunks sur TAXONOMIE_WORKSPACE

[source,bash]
----
./gradlew vibecodingGovernance --inspect <chunkId>

Options:
--chunkId <id> : Affiche les details d'un chunk specifique
--format <json|adoc|yaml> : Format de sortie
--diff <chunkId1 chunkId2> : Affiche les differences entre 2 chunks
----

[source,bash]
----
./gradlew vibecodingGovernance --trace <ruleId>

Options:
--ruleId <id> : Affiche la trace d'une regle (source → chunk → compile → enforce)
--from <timestamp> : Trace a partir de

--history <nbSessions> : Trace les N dernieres sessions

== Conclusion

La governance agentique est le **seul manque** dans le vibecoding actuel.
Sans cette brique, le LLM ne peut pas consulter TOUS les fichiers du workspace (seulement le code applicatif).

Le pipeline VibecodingGover
nanceComplete doit transformer :
- **Littérature textuelle** (AGENT.adoc, INDEX.adoc, SESSION_CHECKLIST.adoc, etc.)
- → **Chunks ontologisés** (chunkId, verb, domain, dagLevel, circle, weight)
- → **Contraintes exécutables** (ToolRegistry pre/post hooks, gates, validation)
- → **Contexte augmenté complet** (EAGER 40% + RAG 30% + Graphify 20% + Ressources 10%)

C'est le **chaînon manquant** entre "agent qui lit du code" et "agent qui utilise Tout le workspace".
