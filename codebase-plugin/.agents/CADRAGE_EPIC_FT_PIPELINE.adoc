== Contexte

La vision globale (`WORKSPACE_AS_PRODUCT.adoc:642-658`) assigne à
codebase-gradle la propriété du **pipeline de fine-tuning** des experts
spécialisés (CDA/FPA). Or l'EPIC 5 "Fine-tuning" historique a été migré vers
training-gradle TRN-8 (`❌ À FAIRE`) — mais TRN-8 mélange deux natures
distinctes :

* **Pipeline N1** (générique, infrastructure) — la machinerie réutilisable
  qui prend `(dataset, baseModel, outputModelName)` et produit un modèle
  fine-tuné exposé via Ollama. Continual pre-training, validation,
  publishing. Indépendante du domaine métier (CDA, FPA, ou autre).
* **Experts N2** (métier, training-gradle) — les recettes spécifiques :
  quels datasets (corpus AFNOR/REAC), quels modèles de base, quels noms
  d'expert, la curation pédagogique Bloom/Qualiopi. Le "quoi" et "pourquoi".

Cette séparation suit le pattern DDD déjà en place pour LLM/RAG/anonymisation :
codebase possède `LlmBuildService` (pool générique N1), training/slider/codex
l'appellent pour leurs besoins métier N2. Le pipeline de fine-tuning suit la
même ligne — socle N1 générique, recettes métier N2.

== Audit — Briques existantes réutilisables

=== Domaine `codebase.koog.expert` (13 fichiers)

Le pipeline FT s'interface naturellement avec ce domaine. Il gère
l'**exposition** des experts fine-tunés (modèle déjà enregistré dans Ollama,
manifest JSON consommé par slider/plantuml/bakery).

* `ExpertExposureTask` — tâche Gradle `exposeExperts`, génère manifest JSON
* `ExpertRegistry` — registre runtime des experts (domain, modelName, baseUrl)
* `ExpertAgent` — wrapper `OllamaChatModel` pour appels experts
* `ExpertManifestReader` — lecture manifest côté consommateurs
* `ExpertCallPipeline` / `ExpertCallRecord` / `ExpertCallRepository` —
  pipeline d'appel + traçabilité
* `ExpertContracts` / `ExpertDomain` / `ExpertExposureContracts` —
  contrats N1

**Ce qui manque** pour boucler le pipeline FT : la **création** du modèle
fine-tuné (dataset prep + continual pre-training + export GGUF + push Ollama).
L'exposition est déjà là, la fabrication non.

== Décisions architecturales

. **EPIC codebase-only** — pipeline FT générique N1, pas de code training.
  Training-gradle TRN-8 reformulé en recettes N2 qui consomment le pipeline.

. **Domaine `codebase.finetuning`** (nouveau, 7ème sous `codebase`) —
  pipeline FT pur, Gradle-free, unit-testable, pattern `capsule.feed`/
  `capsule.transcript` (domaine pur + port/adapter).

. **`FineTuningPipeline`** — fun interface `fineTune(request): Result`
  où `FineTuningRequest(baseModel, dataset, outputModelName, hyperparams)`.
  Domaine Gradle-free, unit-testable avec fake.

. **`OllamaFineTunerAdapter`** — adapter bridge Ollama API (create model
  from Modelfile, push to registry). Pattern `ChatModelTranscriptEnhancer`
  (port + adapter langchain4j/Ollama).

. **Tâches Gradle** :
  - `prepareFineTuningDataset` — groupe `finetuning`, assemble dataset
    (corpus cible 10% + base model Modelfile)
  - `fineTuneExpert` — groupe `finetuning`, exécute continual pre-training
    via `FineTuningPipeline`, produit GGUF
  - `publishExpertToOllama` — groupe `finetuning`, push GGUF vers Ollama
    registry + register dans `ExpertRegistry` (boucle avec domaine expert
    existant)

. **Cycle itératif TDD IA** — pattern `KoogPlanningGraph` réutilisé :
  `FineTuningGraph` (koog `strategy<FineTuningState, FineTuningState>`)
  3 nœuds propose/train/validate + edges conditionnels (convergence score,
  backtracking, maxIterations). Méthode `execute` séquentielle pattern
  `KoogAugmentedContextGraph`.

. **Continual pre-training 10% corpus** — méthode ACL 2024 arXiv 2311.08545
  (déjà référencée `BenchmarkRunner.kt:195`). Hyperparamètre
  `corpusRatio = 0.10` configurable, default backward compat.

. **Contexte augmenté** — `AugmentedContext` (EPIC SUBGRAPH) consommé
  pour enrichir les itérations : historique des fine-tunings précédents,
  patterns d'erreur, scores de validation. Pattern notebook-gradle
  "conversation persistante" (ARCHITECTURE.adoc:372-398).

. **BYOK** — `api-key-pool-gradle` (N0) consommé pour les appels gros
  modèle API. Ollama local gratuit pour décideur. Zéro coût Edster.cloud.

. **Output GGUF + manifest** — fine-tune produit un modèle GGUF poussé
  vers Ollama registry, puis enregistré dans `ExpertRegistry` (domaine
  expert existant) + manifest JSON via `ExpertExposureTask` (boucle fermée
  fabrication→exposition).

. **Validation** — `ValidationResult` sealed (pattern `DeckContextValidator`
  slider SLD-8.3) — score de qualité du modèle fine-tuné (perplexity,
  human-eval, expert-eval). Seuil configurable, default backward compat.

. **Zéro bump BOM** — pipeline FT consomme les contrats N0 existants
  (agent-contracts 0.0.3, codebase-contracts 0.0.2). Pas de nouveau contrat
  N0. Le domaine `codebase.finetuning` est interne N1.

. **Pas de runtime Colab** — notebook-gradle concevait un runtime client
  Colab. FT-PIPELINE s'exécute en CI/CD Gradle (GitHub Actions Docker +
  Ollama), pas en notebook interactif. Le runtime Colab est hors scope
  codebase — relèverait d'un futur borough runtime si besoin.

. **Cucumber BDD** — `codebase_finetuning.feature` scénarios `@finetuning`
  (runner dédié pattern S-082, `CucumberTaskSpec` 38e) :
  - pipeline complet dataset→GGUF→manifest
  - cycle itératif convergence/backtracking
  - fallback degraded (Ollama unavailable → skip + warn)
  - validation seuil
  - BYOK pool rotation

. **Budget tokens** — fine-tuning lourd (10% corpus, itérations). Pool
  `LlmBuildService` rotation 11437-11465 (29 ports) + 2 modèles autorisés
  (`gpt-oss:120b-cloud`, `gemma4:31b-cloud`). Pas de nouveau port/modèle.

. **EPIC notebook-gradle caduque** — le vestige LA HAVANA n'est pas
  implémenté et ne le sera pas. Sa conception est absorbée par FT-PIPELINE
  (pipeline) + éventuel futur borough cockpit (dashboard). Le backlog
  notebook-gradle (8 EPICs) est déclaré caduc — la spécification est
  récupérée, pas le périmètre produit.

. **TRN-8 reformulé** — training-gradle TRN-8 "Pipeline fine-tuning experts
  CDA/FPA" devient "Recettes CDA/FPA consommant FT-PIPELINE". Les recettes
  spécifient les datasets (corpus AFNOR/REAC), modèles de base, noms
  d'expert, mais appellent `fineTuneExpert` de codebase. Dépendance N2→N1
  propre.
